# Official documentation findings

Verified 2026-10-10 against current official documentation. This research supports the build plan; it does not change its constraints.

## SES v2 sending and quota

- The required API shape is supported: SES v2 `SendEmail` accepts `Content.Raw.Data`, `Destination`, `ConfigurationSetName`, and `EmailTags`. Raw content must be a valid MIME message with headers and body; the Go SDK performs the required base64 transport encoding. Use the SES v2 `sesv2` Go client and `SendEmail`, not the SES v1 raw API. [SES raw email guide](https://docs.aws.amazon.com/ses/latest/dg/send-email-raw.html), [SendEmail API](https://docs.aws.amazon.com/ses/latest/APIReference-V2/API_SendEmail.html), [RawMessage API](https://docs.aws.amazon.com/ses/latest/APIReference-V2/API_RawMessage.html), [AWS SDK for Go v2 sesv2 package](https://pkg.go.dev/github.com/aws/aws-sdk-go-v2/service/sesv2)
- `GetAccount` returns the regional `SendQuota` object, including the daily quota, sent amount, and maximum send rate. Read `MaxSendRate`, `Max24HourSend`, and `SentLast24Hours` from this API at runtime. The response also exposes `SendingEnabled`; check it and pause/report when sending is disabled. Quotas are account and region specific. [GetAccount API](https://docs.aws.amazon.com/ses/latest/APIReference-V2/API_GetAccount.html)
- SDK v2's default `retry.Standard` allows 3 total attempts and includes a client-side token rate limiter. The SDK documents `aws.NoOpRetryer` as disabling retries; alternatively construct `retry.Standard` with `MaxAttempts: 1` and `RateLimiter: ratelimit.None` if the app wants SDK backoff/retry classification but to own attempt scheduling. For the plan's complete application-owned retry/backoff policy, configure a no-op retryer per SES client, then let the worker classify and retry errors. [AWS SDK for Go v2 retry documentation](https://docs.aws.amazon.com/sdk-for-go/v2/developer-guide/configure-retries-timeouts.html)

## SNS and SQS event ingestion

- SNS recommends signature verification for HTTPS notifications and subscription confirmations. Verify before processing, require the expected `TopicArn`, retrieve signing certificates only over HTTPS from an SNS signing URL, and validate their certificate chain. Accept only expected SNS signature versions, with v2/SHA-256 preferred. An HTTPS endpoint confirms a subscription by requesting its `SubscribeURL`, but only after validating the confirmation message. [SNS signature verification](https://docs.aws.amazon.com/sns/latest/dg/sns-verify-signature-of-message.html), [HTTP endpoint preparation and confirmation](https://docs.aws.amazon.com/sns/latest/dg/SendMessageToHttp.prepare.html)
- SNS-to-SQS is a documented supported fanout pattern. Grant the topic `sqs:SendMessage` through the queue policy, subscribe the queue to the topic, and allow the app to receive and delete. Long poll with `WaitTimeSeconds: 20` (maximum), and set the HTTP response/read timeout longer than the wait. Delete only after durable processing; use the visibility timeout and a DLQ/redrive policy to recover poison messages. [SNS to SQS setup](https://docs.aws.amazon.com/sns/latest/dg/subscribe-sqs-queue-to-sns-topic.html), [SQS long-poll guidance](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/best-practices-setting-up-long-polling.html), [SQS visibility timeout](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/working-with-visibility-timeouts.html)

## Bulk sender unsubscribe headers

- Gmail's current sender guidance requires marketing/subscription messages at bulk volume to support one-click unsubscribe and include a clearly visible body unsubscribe link. Its RFC 8058 guidance requires both `List-Unsubscribe` with an HTTPS URL and `List-Unsubscribe-Post: List-Unsubscribe=One-Click`; a `mailto:` link alone does not satisfy one-click. The HTTP POST must unsubscribe without further interaction, and Gmail says requests should be honored within 48 hours. The plan's immediate POST behavior exceeds that window. Keep a separate visible body link as well. [Gmail sender requirements](https://support.google.com/mail/answer/81126?hl=en), [Gmail one-click FAQ](https://support.google.com/mail/answer/14229414?hl=en)
- Include both unsubscribe headers on the raw MIME message per recipient. A `mailto:` may be additional, but should not replace HTTPS. Preserve the standard header spelling and exact POST value. [Gmail one-click FAQ](https://support.google.com/mail/answer/14229414?hl=en)

## GrapesJS newsletter preset versus TinyMCE full-page HTML

- GrapesJS's newsletter preset is purpose-built for constructing newsletter layouts, offers blocks and an export command that can inline CSS. Its normal output path is generated canvas HTML plus CSS (`getHtml()` and `getCss()`), and its project JSON is intended for restoring the editor project. This is a builder/export workflow, not a lossless parser/serializer for arbitrary existing full documents. The docs do not promise preservation of unknown markup, ordering, conditional comments, or exact source formatting. Given the existing Sendy templates and raw-HTML source-of-truth requirement, importing a full document into GrapesJS risks changing its structure and should not be the default WYSIWYG round-trip. [GrapesJS overview](https://grapesjs.com/docs/), [newsletter preset](https://github.com/GrapesJS/preset-newsletter), [editor API](https://github.com/GrapesJS/grapesjs/blob/dev/docs/api/editor.md)
- TinyMCE's Full Page HTML plugin explicitly reads and returns complete documents, including head and doctype, through `getContent()`/`setContent()`. It better fits full-document editing, but it is a paid plugin, classic-mode only, and content passes TinyMCE's sanitization/schema. Its documentation explicitly warns that nonstandard elements can be removed unless configured. It therefore does not guarantee byte-identical round-trip of email-specific conditional comments and unusual markup either. [TinyMCE Full Page HTML docs](https://www.tiny.cloud/docs/tinymce/latest/fullpagehtml/)
- Actionable choice: keep CodeMirror/raw HTML as the authoritative mode. If adding WYSIWYG, TinyMCE Full Page HTML is the closer fit for complete documents, subject to its subscription and sanitizer/schema review. Always compare saved output to the original and show a diff/confirm before applying changes. GrapesJS is a better fit for creating new structured newsletters from supported blocks than editing arbitrary legacy full HTML.
